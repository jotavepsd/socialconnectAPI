Aula 04: Persistência com JPA e Migrations

Tópicos Especiais em Sistemas para Internet III | Material Didático Completo

🏆 REGRA DE OURO DA DISCIPLINA: Chaves primárias no banco de dados DEVEM usar o prefixo id_ (ex: id_beneficiario, id_doacao).

🎯 Objetivos de Aprendizagem

Ao final desta aula, você será capaz de:

  • Compreender os riscos do ddl-auto em ambientes reais (perda de dados, inconsistência).
  • Configurar o Flyway como ferramenta de controle de versão de banco de dados.
  • Criar scripts de migration seguindo o padrão V<numero>__<descricao>.sql.
  • Aplicar rigorosamente o padrão id_ para chaves primárias.
  • Validar o mapeamento JPA contra um esquema gerenciado pelo Flyway.

⚠️ O Problema do ddl-auto

Nas aulas anteriores, configuramos o Hibernate para gerenciar automaticamente o esquema do banco:

spring.jpa.hibernate.ddl-auto=create-drop

Por que isso é PERIGOSO em produção?

❌ Riscos do create-drop:
  • Perda de dados: Apaga todas as tabelas ao reiniciar a aplicação.
  • Inconsistência: update não remove colunas antigas nem aplica renomeações.
  • Sem histórico: Não há registro de como o banco evoluiu ao longo do tempo.
  • Ambientes divergentes: Dev, homologação e produção ficam com esquemas diferentes.

Exemplo Prático do Problema

Imagine que você adicionou uma coluna telefone na Entity Beneficiario e usou ddl-auto=update:

  • O Hibernate adiciona a coluna no banco.
  • Mas e se você precisar renomear a coluna de telefone para contato?
  • O update não faz isso. Ele cria uma nova coluna contato e mantém a antiga telefone vazia.
  • Resultado: dados perdidos, esquema inconsistente.
💡 Conclusão: O Hibernate é ótimo para mapear objetos, mas péssimo para gerenciar a evolução do esquema do banco. Precisamos de uma ferramenta especializada.

💡 A Solução: Database Migrations com Flyway

O que é Database Migration?

Controle de versão do esquema do banco de dados, similar ao Git para código. Cada mudança no banco é registrada em um arquivo SQL versionado.

Ferramenta: Flyway

O Flyway é uma biblioteca Java que:

  • Executa scripts SQL em ordem (V1, V2, V3...).
  • Garante que todos os ambientes (dev, homologação, produção) tenham o mesmo esquema.
  • Rastreia o que já foi executado na tabela flyway_schema_history.
  • Impede que o mesmo script seja executado duas vezes.

Fluxo de Trabalho

Script SQL
(V1__create_table.sql)
→
Flyway
(Executa)
→
Banco Atualizado
(Tabela criada)
→
Hibernate
(Apenas valida)
✅ Benefícios:
  • Reprodutibilidade: Qualquer desenvolvedor pode criar o banco do zero executando os scripts.
  • Rastreabilidade: O histórico de mudanças fica no Git junto com o código.
  • Segurança: Mudanças são revisadas em Pull Requests antes de serem aplicadas.
  • Portabilidade: Funciona com H2, PostgreSQL, MySQL, Oracle, etc.

🏆 A Regra de Ouro: Padrão id_

Na disciplina, adotamos uma convenção rigorosa de nomenclatura para chaves primárias:

Camada Convenção Exemplo Justificativa
Banco de Dados snake_case com prefixo id_ id_beneficiario Legibilidade em SQL, evita ambiguidade em joins
Java (Atributo) camelCase idBeneficiario Convenção Java, compatibilidade com Lombok
Ponte (JPA) @Column(name = "...") @Column(name = "id_beneficiario") Mapeia a variável Java para a coluna SQL
⚠️ Erro Comum: Tentar nomear o atributo Java como id_beneficiario (com underscore).
Por que está errado? O Lombok gera getters baseados no nome da variável. Se a variável for id_beneficiario, o getter será getId_beneficiario(), violando a convenção Java e causando confusão.
✅ Forma Correta: 
@Column(name = "id_beneficiario") // Nome da coluna no banco
private Long idBeneficiario; // Nome da variável em Java (camelCase)

📋 Convenção Completa de Nomenclatura

Tabelas

  • Plural: beneficiarios, doadores, doacoes
  • snake_case: itens_doacao (não itensDoacao)

Colunas

  • Chaves primárias: id_<entidade> (ex: id_beneficiario)
  • Chaves estrangeiras: id_<entidade_referenciada> (ex: id_doador na tabela doacoes)
  • Demais colunas: snake_case (ex: data_cadastro, situacao_vulnerabilidade)

Índices

  • Padrão: idx_<tabela>_<coluna>
  • Exemplo: idx_beneficiarios_cpf
💡 Dica: Siga essas convenções em todos os scripts de migration. Isso facilita a leitura do SQL e a manutenção do banco ao longo do tempo.

🔄 Como o Flyway Funciona

Nomenclatura dos Scripts

O Flyway exige um formato específico para os nomes dos arquivos:

V<numero>__<descricao>.sql

Exemplos válidos:

  • V1__create_beneficiarios_table.sql
  • V2__create_doadores_table.sql
  • V3__add_telefone_to_beneficiarios.sql
⚠️ Atenção: São dois underlines (__) entre o número e a descrição. Um underline só (V1_create...) não funciona.

Tabela de Histórico

O Flyway cria automaticamente uma tabela chamada flyway_schema_history no banco, que registra:

  • Qual script foi executado.
  • Quando foi executado.
  • Quem executou.
  • Checksum do arquivo (para detectar alterações indevidas).

Ordem de Execução

O Flyway executa os scripts em ordem alfabética/numérica:

  1. V1__create_beneficiarios_table.sql
  2. V2__create_doadores_table.sql
  3. V3__add_telefone_to_beneficiarios.sql
💡 Importante: Nunca altere um script que já foi executado em produção. Se precisar fazer uma mudança, crie um novo script (V4__...).

1️⃣ Adicionar Dependência do Flyway

No arquivo pom.xml, adicione a dependência do Flyway:

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
💡 Nota: O Spring Boot gerencia a versão do Flyway automaticamente via BOM (Bill of Materials). Você não precisa especificar a versão.

2️⃣ Configurar application.properties

Mudança Crítica: ddl-auto

# ANTES (Aula 03):
spring.jpa.hibernate.ddl-auto=create-drop

# AGORA (Aula 04 em diante):
spring.jpa.hibernate.ddl-auto=validate

O que mudou?

  • create-drop: O Hibernate cria as tabelas ao iniciar e apaga ao fechar.
  • validate: O Hibernate apenas verifica se o esquema do banco bate com as Entities. Ele NÃO cria, altera ou apaga tabelas.

Configuração do Flyway

# ==========================================================
# Flyway (Migrations)
# ==========================================================
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.flyway.baseline-on-migrate=true

Explicação das propriedades:

  • spring.flyway.enabled=true: Ativa o Flyway.
  • spring.flyway.locations=classpath:db/migration: Indica onde os scripts estão localizados.
  • spring.flyway.baseline-on-migrate=true: Cria uma linha de base se o banco já existir (útil para bancos legados).

3️⃣ Estrutura de Pastas

Crie a seguinte estrutura de diretórios:

src/main/resources/
 └── db/
      └── migration/
           └── V1__create_beneficiarios_table.sql
💡 Dica: No IntelliJ ou VS Code, clique com o botão direito na pasta resources → New → Directory → db/migration.

4️⃣ Criar o Script de Migration

Crie o arquivo V1__create_beneficiarios_table.sql dentro da pasta db/migration:

-- Migration: V1 - Criação da tabela de beneficiários
-- Padrão da disciplina: chaves primárias com prefixo 'id_'

CREATE TABLE beneficiarios (
    id_beneficiario BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    cpf VARCHAR(14) NOT NULL UNIQUE,
    telefone VARCHAR(20),
    endereco VARCHAR(255),
    situacao_vulnerabilidade VARCHAR(500),
    data_cadastro DATE NOT NULL
);

-- Índice opcional para otimizar buscas por CPF (boa prática)
CREATE INDEX idx_beneficiarios_cpf ON beneficiarios(cpf);

Pontos de Atenção:

  • Chave primária: id_beneficiario BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
    • BIGINT: Tipo recomendado para chaves primárias (evita estouro em sistemas reais).
    • GENERATED BY DEFAULT AS IDENTITY: Padrão SQL que funciona no H2 e PostgreSQL (portabilidade).
    • PRIMARY KEY: Define a coluna como chave primária.
  • Colunas: Seguem o padrão snake_case (situacao_vulnerabilidade, data_cadastro).
  • Índice: idx_beneficiarios_cpf otimiza buscas por CPF (boa prática para colunas frequentemente consultadas).
✅ Portabilidade: O uso de GENERATED BY DEFAULT AS IDENTITY garante que o script funcione tanto no H2 (desenvolvimento) quanto no PostgreSQL (produção), sem necessidade de ajustes.

5️⃣ Validar o Mapeamento JPA

A Entity Beneficiario.java deve estar mapeada corretamente para bater com o esquema criado pelo Flyway:

package br.com.socialconnect.api.beneficiarios.model;

import jakarta.persistence.*;
import lombok.*;
import java.time.LocalDate;

@Entity
@Table(name = "beneficiarios")
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Beneficiario {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_beneficiario") // ⚠️ Deve bater EXATAMENTE com o SQL
    private Long idBeneficiario; // camelCase no Java

    @Column(nullable = false, length = 150)
    private String nome;

    @Column(nullable = false, unique = true, length = 14)
    private String cpf;

    @Column(length = 20)
    private String telefone;

    @Column(length = 255)
    private String endereco;

    @Column(name = "situacao_vulnerabilidade", length = 500)
    private String situacaoVulnerabilidade;

    @Column(name = "data_cadastro", nullable = false)
    private LocalDate dataCadastro;
}

Validação Automática

Com ddl-auto=validate, o Hibernate verifica ao iniciar se:

  • O nome da tabela bate (beneficiarios).
  • O nome das colunas bate (id_beneficiario, situacao_vulnerabilidade, etc.).
  • Os tipos de dados são compatíveis (BIGINT ↔ Long, VARCHAR ↔ String, etc.).
  • As restrições são respeitadas (NOT NULL, UNIQUE, etc.).
⚠️ Erro Comum: Se o nome da coluna no SQL não bater com o @Column(name = "..."), o Hibernate lança um erro ao iniciar: 
org.hibernate.tool.schema.spi.SchemaManagementException: 
Schema-validation: missing column [id_beneficiario]

🔄 Dinâmica: Revisão Cruzada de Esquema

Atividade em Duplas (30 min)

Desafio:

Cada dupla deve escrever:

  1. Script V2__create_doadores_table.sql
  2. Entity Doador.java correspondente

Requisitos:

  • Chave primária: id_doador
  • Colunas: nome, tipo (PESSOA_FISICA ou PESSOA_JURIDICA), email, telefone
  • Entity com @Column(name = "...") para todas as colunas snake_case

Revisão Cruzada:

As duplas trocam de lugar e validam o código do colega usando este checklist:

  • [ ] O arquivo está na pasta db/migration?
  • [ ] O nome do arquivo segue o padrão V<numero>__<descricao>.sql?
  • [ ] A chave primária tem o prefixo id_?
  • [ ] A Entity usa @Column(name = "...") corretamente?
  • [ ] Os tipos de dados são compatíveis (SQL ↔ Java)?
💡 Objetivo Pedagógico: A revisão cruzada simula um Pull Request Review real, onde os alunos praticam a leitura crítica de código e a comunicação técnica.

⚠️ Armadilhas Comuns

1. Nome do arquivo de migration errado

❌ Errado: V1_create_table.sql (um underline)

✅ Correto: V1__create_table.sql (dois underlines)

Sintoma: O Flyway ignora o arquivo ou lança erro de sintaxe.

2. Esquecer de mudar o ddl-auto

❌ Errado: Deixar spring.jpa.hibernate.ddl-auto=create-drop

✅ Correto: spring.jpa.hibernate.ddl-auto=validate

Sintoma: O Hibernate conflita com o Flyway, criando/apagando tabelas inesperadamente.

3. Divergência de nomes

❌ Errado: SQL com id_beneficiario, mas Entity sem @Column(name = "id_beneficiario")

✅ Correto: Sempre mapear explicitamente com @Column

Sintoma: Erro Schema-validation: missing column [id_beneficiario] ao iniciar.

4. Tipo incompatível

❌ Errado: SQL com INT, Java com Long

✅ Correto: SQL com BIGINT, Java com Long

Sintoma: Erro de validação de esquema ou estouro de capacidade em produção.

5. Alterar script já executado

❌ Errado: Modificar V1__create_table.sql depois que ele já foi executado

✅ Correto: Criar um novo script V2__alter_table.sql

Sintoma: Erro de checksum no Flyway (Checksum mismatch).

📝 Resumo da Aula

  • Flyway substitui o ddl-auto para controle de versão do banco de dados.
  • Scripts seguem o padrão V<numero>__<descricao>.sql (dois underlines).
  • Padrão id_ é obrigatório para chaves primárias no banco de dados.
  • @Column(name = "...") faz a ponte entre Java (camelCase) e SQL (snake_case).
  • ddl-auto=validate garante que o Hibernate apenas confira o esquema, sem alterá-lo.
  • Revisão cruzada simula Pull Request Reviews e fortalece a colaboração.
