🎯 Objetivos de Aprendizagem

Ao final desta aula, você será capaz de:

📋 Métodos HTTP e Suas Semânticas

A semântica HTTP define o significado de cada método. Usar o método errado é como usar um verbo errado em uma frase: a mensagem chega, mas causa confusão.

Método Semântica Idempotente? Seguro? Exemplo SocialConnect
GET Ler/consultar recurso ✅ Sim ✅ Sim GET /api/v1/beneficiarios/1
POST Criar novo recurso ❌ Não ❌ Não POST /api/v1/beneficiarios
PUT Substituir recurso por completo ✅ Sim ❌ Não PUT /api/v1/beneficiarios/1
PATCH Atualizar parcialmente ❌ Não* ❌ Não PATCH /api/v1/beneficiarios/1
DELETE Remover recurso ✅ Sim ❌ Não DELETE /api/v1/beneficiarios/1
💡 Conceitos-chave:
  • Seguro: O método não altera o estado do servidor. Apenas GET e HEAD são seguros.
  • Idempotente: Executar 1x ou 100x produz o mesmo resultado. POST é o único método CRUD que NÃO é idempotente.

🏷️ Códigos de Status HTTP

Os status codes são a linguagem universal da API. O Front-end depende deles para tomar decisões (ex: redirecionar após login, mostrar mensagem de erro).

2xx — Sucesso

CódigoSignificadoQuando Usar
200 OKRequisição bem-sucedidaGET, PUT, PATCH com corpo de resposta
201 CreatedRecurso criadoPOST (com cabeçalho Location)
204 No ContentSucesso sem corpoDELETE, PUT sem retorno

4xx — Erro do Cliente

CódigoSignificadoQuando Usar
400 Bad RequestRequisição malformadaJSON inválido, campos faltando
404 Not FoundRecurso não existeID inexistente
409 ConflictConflito de estadoCPF já cadastrado
422 UnprocessableSemântica inválidaCPF com formato correto mas inválido

5xx — Erro do Servidor

CódigoSignificadoQuando Usar
500 Internal ErrorErro inesperadoExceção não tratada (NPE, DB down)
⚠️ Erro Comum: Retornar 200 OK para tudo, inclusive erros. Isso quebra a semântica e impede o Front-end de reagir corretamente. Exemplo: retornar 200 com {"erro": "não encontrado"} em vez de 404.

📎 Cabeçalhos HTTP Importantes

CabeçalhoDireçãoUso
Content-TypeRequest/ResponseIndica o formato do corpo (application/json)
AcceptRequestIndica o formato que o cliente aceita
LocationResponseURL do recurso criado (obrigatório no 201)
AuthorizationRequestToken de autenticação (Bearer xxx)
Idempotency-KeyRequestChave única para evitar POSTs duplicados
💡 Cabeçalho Location no POST:
Quando você cria um recurso com POST, a resposta 201 Created DEVE incluir o cabeçalho Location apontando para o novo recurso: 
HTTP/1.1 201 Created
Location: /api/v1/beneficiarios/42
Content-Type: application/json

⚠️ O Problema do DTO Único

Nas aulas anteriores, usamos um único BeneficiarioDTO para entrada e saída. Isso funciona para protótipos, mas causa problemas em APIs reais:

Problema 1: Campos de Resposta no Request

O cliente pode enviar idBeneficiario e dataCadastro no POST, tentando forçar valores que deveriam ser gerados pelo servidor.

Problema 2: Campos Sensíveis na Resposta

Se a Entity tiver um campo senha ou observacoesInternas, ele pode vazar na resposta JSON se você retornar a Entity diretamente.

Problema 3: Acoplamento

Mudanças na Entity (ex: adicionar campo de auditoria) afetam automaticamente o contrato da API, quebrando clientes existentes.

⚠️ Regra: Nunca exponha a Entity JPA diretamente no Controller. Sempre use DTOs. E em APIs reais, separe DTOs de Request e Response.

✅ Solução: DTOs Separados (Request vs Response)

Fluxo de Dados

OperaçãoEntrada (Request)Saída (Response)
POST (Criar)BeneficiarioRequestDTOBeneficiarioResponseDTO
PUT (Substituir)BeneficiarioRequestDTOBeneficiarioResponseDTO
PATCH (Parcial)BeneficiarioPatchDTOBeneficiarioResponseDTO
GET (Ler)—BeneficiarioResponseDTO
✅ Benefícios:
  • Segurança: O cliente não pode forçar campos do servidor (ex: idBeneficiario).
  • Clareza: O contrato da API documenta exatamente o que entra e o que sai.
  • Flexibilidade: A resposta pode incluir campos calculados (ex: totalDoacoes) que não existem na Entity.

💻 Implementação dos DTOs

BeneficiarioRequestDTO.java

package br.com.socialconnect.api.beneficiarios.dto;

import jakarta.validation.constraints.*;

// DTO de ENTRADA: apenas campos que o cliente pode enviar
public record BeneficiarioRequestDTO(

    @NotBlank(message = "Nome é obrigatório")
    @Size(max = 150, message = "Nome deve ter no máximo 150 caracteres")
    String nome,

    @NotBlank(message = "CPF é obrigatório")
    @Pattern(regexp = "\\d{11}|\\d{14}", message = "CPF inválido")
    String cpf,

    String telefone,
    String endereco,
    String situacaoVulnerabilidade

) {}

BeneficiarioResponseDTO.java

package br.com.socialconnect.api.beneficiarios.dto;

import java.time.LocalDate;

// DTO de SAÍDA: inclui campos gerados pelo servidor
public record BeneficiarioResponseDTO(
    Long idBeneficiario,
    String nome,
    String cpf,
    String telefone,
    String endereco,
    String situacaoVulnerabilidade,
    LocalDate dataCadastro

BeneficiarioPatchDTO.java

Para o PATCH, todos os campos são opcionais (o cliente envia apenas o que quer alterar):

package br.com.socialconnect.api.beneficiarios.dto;

// DTO para PATCH: todos os campos opcionais
public record BeneficiarioPatchDTO(
    String nome,
    String telefone,
    String endereco,
    String situacaoVulnerabilidade
) {}
💡 Nota sobre validação: As anotações @NotBlank, @Size e @Pattern são do Jakarta Bean Validation. Elas serão exploradas em profundidade na Aula 06, mas já as incluímos aqui para demonstrar a separação de responsabilidades.

🔄 PUT vs PATCH: Quando Usar Cada Um?

PUT — Substituição Total

O cliente envia todos os campos do recurso. Campos ausentes são definidos como null.

PUT /api/v1/beneficiarios/1 
{
  "nome": "Maria da Silva Santos",
  "cpf": "12345678900",
  "telefone": "11988887777",
  "endereco": "Rua Nova, 456",
  "situacaoVulnerabilidade": "Renda familiar baixa"
}
// Se "telefone" fosse omitido, ele seria definido como null no banco.

PATCH — Atualização Parcial

O cliente envia apenas os campos que deseja alterar. Campos ausentes permanecem inalterados.

PATCH /api/v1/beneficiarios/1 
{
  "telefone": "11988887777"
}
// Apenas o telefone é atualizado. Os demais campos permanecem iguais.
CaracterísticaPUTPATCH
Campos enviadosTodosApenas os alterados
Campos ausentesViram nullPermanecem inalterados
Idempotente✅ Sim❌ Não (geralmente)
Caso de usoEdição completa de formulárioEdição rápida de um campo

💻 Controller Completo (CRUD + Paginação + Filtros)

package br.com.socialconnect.api.beneficiarios.controller;

import br.com.socialconnect.api.beneficiarios.dto.*;
import br.com.socialconnect.api.beneficiarios.service.BeneficiarioService;
import jakarta.validation.Valid;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.web.PageableDefault;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;

@RestController
@RequestMapping("/api/v1/beneficiarios")
public class BeneficiarioController {

    private final BeneficiarioService service;

    public BeneficiarioController(BeneficiarioService service) {
        this.service = service;
    }

    // ✅ GET com paginação e filtros
    @GetMapping
    public ResponseEntity<Page<BeneficiarioResponseDTO>> listar(
            @RequestParam(required = false) String nome,
            @RequestParam(required = false) String cpf,
            @PageableDefault(size = 10, sort = "nome") Pageable pageable) {
        return ResponseEntity.ok(service.listar(nome, cpf, pageable));
    }

    // ✅ GET por ID
    @GetMapping("/{idBeneficiario}")
    public ResponseEntity<BeneficiarioResponseDTO> buscarPorId(
            @PathVariable Long idBeneficiario) {
        return ResponseEntity.ok(service.buscarPorId(idBeneficiario));
    }

    // ✅ POST com validação e 201 Created
    @PostMapping
    public ResponseEntity<BeneficiarioResponseDTO> criar(
            @Valid @RequestBody BeneficiarioRequestDTO dto) {
        BeneficiarioResponseDTO salvo = service.criar(dto);
        URI location = URI.create("/api/v1/beneficiarios/" + salvo.idBeneficiario());
        return ResponseEntity.created(location).body(salvo);
    }

    // ✅ PUT (substituição total)
    @PutMapping("/{idBeneficiario}")
    public ResponseEntity<BeneficiarioResponseDTO> atualizar(
            @PathVariable Long idBeneficiario,
            @Valid @RequestBody BeneficiarioRequestDTO dto) {
        return ResponseEntity.ok(service.atualizar(idBeneficiario, dto));
    }

    // ✅ PATCH (atualização parcial)
    @PatchMapping("/{idBeneficiario}")
    public ResponseEntity<BeneficiarioResponseDTO> atualizarParcial(
            @PathVariable Long idBeneficiario,
            @RequestBody BeneficiarioPatchDTO dto) {
        return ResponseEntity.ok(service.atualizarParcial(idBeneficiario, dto));
    }

    // ✅ DELETE com 204 No Content
    @DeleteMapping("/{idBeneficiario}")
    public ResponseEntity<Void> deletar(
            @PathVariable Long idBeneficiario) {
        service.deletar(idBeneficiario);
        return ResponseEntity.noContent().build();
    }
}

💻 Service Completo (CRUD + Paginação + Filtros)

package br.com.socialconnect.api.beneficiarios.service;

import br.com.socialconnect.api.beneficiarios.dto.*;
import br.com.socialconnect.api.beneficiarios.model.Beneficiario;
import br.com.socialconnect.api.beneficiarios.repository.BeneficiarioRepository;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.stereotype.Service;

import java.time.LocalDate;

@Service
public class BeneficiarioService {

    private final BeneficiarioRepository repository;

    public BeneficiarioService(BeneficiarioRepository repository) {
        this.repository = repository;
    }

    // ✅ Listar com paginação e filtros opcionais
    public Page<BeneficiarioResponseDTO> listar(
            String nome, String cpf, Pageable pageable) {

        Page<Beneficiario> page;

        if (cpf != null && !cpf.isBlank()) {
            // Filtro exato por CPF (prioridade)
            page = repository.findByCpf(cpf, pageable);
        } else if (nome != null && !nome.isBlank()) {
            // Filtro parcial por nome
            page = repository.findByNomeContainingIgnoreCase(nome, pageable);
        } else {
            // Sem filtro: lista paginada
            page = repository.findAll(pageable);
        }

        return page.map(this::toResponseDTO);
    }

    // ✅ Buscar por ID
    public BeneficiarioResponseDTO buscarPorId(Long idBeneficiario) {
        return repository.findById(idBeneficiario)
                .map(this::toResponseDTO)
                .orElseThrow(() -> new RuntimeException(
                    "Beneficiário não encontrado: " + idBeneficiario));
    }

    // ✅ Criar (POST)
    public BeneficiarioResponseDTO criar(BeneficiarioRequestDTO dto) {
        if (repository.existsByCpf(dto.cpf())) {
            throw new RuntimeException("CPF já cadastrado");
        }
        Beneficiario entity = Beneficiario.builder()
                .nome(dto.nome())
                .cpf(dto.cpf())
                .telefone(dto.telefone())
                .endereco(dto.endereco())
                .situacaoVulnerabilidade(dto.situacaoVulnerabilidade())
                .dataCadastro(LocalDate.now())
                .build();
        return toResponseDTO(repository.save(entity));
    }

    // ✅ Atualizar total (PUT)
    public BeneficiarioResponseDTO atualizar(
            Long idBeneficiario, BeneficiarioRequestDTO dto) {
        Beneficiario entity = repository.findById(idBeneficiario)
                .orElseThrow(() -> new RuntimeException("Não encontrado"));

        entity.setNome(dto.nome());
        entity.setCpf(dto.cpf());
        entity.setTelefone(dto.telefone());
        entity.setEndereco(dto.endereco());
        entity.setSituacaoVulnerabilidade(dto.situacaoVulnerabilidade());

        return toResponseDTO(repository.save(entity));
    }

    // ✅ Atualizar parcial (PATCH)
    public BeneficiarioResponseDTO atualizarParcial(
            Long idBeneficiario, BeneficiarioPatchDTO dto) {
        Beneficiario entity = repository.findById(idBeneficiario)
                .orElseThrow(() -> new RuntimeException("Não encontrado"));

        // Atualiza apenas os campos não-nulos
        if (dto.nome() != null) entity.setNome(dto.nome());
        if (dto.telefone() != null) entity.setTelefone(dto.telefone());
        if (dto.endereco() != null) entity.setEndereco(dto.endereco());
        if (dto.situacaoVulnerabilidade() != null)
            entity.setSituacaoVulnerabilidade(dto.situacaoVulnerabilidade());

        return toResponseDTO(repository.save(entity));
    }

    // ✅ Deletar
    public void deletar(Long idBeneficiario) {
        repository.deleteById(idBeneficiario);
    }

    // Mapeador Entity → Response DTO
    private BeneficiarioResponseDTO toResponseDTO(Beneficiario e) {
        return new BeneficiarioResponseDTO(
            e.getIdBeneficiario(), e.getNome(), e.getCpf(),
            e.getTelefone(), e.getEndereco(),
            e.getSituacaoVulnerabilidade(), e.getDataCadastro()
        );
    }
}

📄 Paginação com Pageable

Por que paginar?

  • Uma ONG pode ter milhares de beneficiários cadastrados.
  • Carregar todos de uma vez consome memória, banda e tempo.
  • O Front-end precisa de páginas para renderizar tabelas e listas.

Como funciona no Spring Data?

O Spring Data JPA suporta paginação nativamente via interface Pageable. Basta adicionar o parâmetro no método do Repository:

// No Repository:
Page<Beneficiario> findByNomeContainingIgnoreCase(String nome, Pageable pageable);

// No Controller:
@GetMapping
public ResponseEntity<Page<BeneficiarioResponseDTO>> listar(
        @PageableDefault(size = 10, sort = "nome") Pageable pageable) {
    return ResponseEntity.ok(service.listarTodos(pageable));
}

Requisição do Cliente:

GET /api/v1/beneficiarios?page=0&size=10&sort=nome,asc

Resposta (JSON):

{
  "content": [
    { "idBeneficiario": 1, "nome": "Ana Silva", ... },
    { "idBeneficiario": 2, "nome": "Bruno Costa", ... }
  ],
  "pageable": { "pageNumber": 0, "pageSize": 10 },
  "totalElements": 150,
  "totalPages": 15,
  "first": true,
  "last": false
}
💡 Page<T> vs List<T>:
Page<T> inclui metadados de paginação (totalElements, totalPages, first, last). O Front-end precisa dessas informações para renderizar os botões de paginação. Nunca retorne List<T> em endpoints que podem retornar muitos registros.

🔍 Filtros Dinâmicos

O Problema

Como permitir que o cliente filtre por múltiplos critérios sem criar um endpoint para cada combinação?

Solução: Query Parameters Opcionais

GET /api/v1/doacoes?dataInicio=2026-01-01&dataFim=2026-08-22&tipo=ALIMENTO

Implementação no Controller:

@GetMapping
public ResponseEntity<Page<DoacaoResponseDTO>> listarDoacoes(
        @RequestParam(required = false) LocalDate dataInicio,
        @RequestParam(required = false) LocalDate dataFim,
        @RequestParam(required = false) String tipo,
        @PageableDefault(size = 20) Pageable pageable) {
    return ResponseEntity.ok(
        doacaoService.listar(dataInicio, dataFim, tipo, pageable)
    );
}
✅ Boas Práticas de Filtros:
  • Use required = false para tornar os filtros opcionais.
  • Combine filtros com paginação (sempre!).
  • Documente os filtros no OpenAPI/Swagger (Aula 06).
  • Para filtros complexos (muitos critérios), considere usar Specification do JPA.

💻 Implementação: Repository com Paginação

Atualize o BeneficiarioRepository para suportar paginação nos métodos de busca:

package br.com.socialconnect.api.beneficiarios.repository;

import br.com.socialconnect.api.beneficiarios.model.Beneficiario;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;

@Repository
public interface BeneficiarioRepository
        extends JpaRepository<Beneficiario, Long> {

    // Paginado: busca por CPF exato
    Page<Beneficiario> findByCpf(String cpf, Pageable pageable);

    // Paginado: busca parcial por nome (case-insensitive)
    Page<Beneficiario> findByNomeContainingIgnoreCase(
        String nome, Pageable pageable);

    // Verificação de unicidade (usado no POST)
    boolean existsByCpf(String cpf);
}
💡 Mágica do Spring Data: Basta adicionar o parâmetro Pageable ao método e mudar o retorno de List para Page. O Spring Data gera automaticamente o SQL com LIMIT e OFFSET.

🔁 Idempotência

Definição Formal

Uma operação é idempotente se executá-la múltiplas vezes produz o mesmo resultado que executá-la uma única vez.

Exemplos Práticos

OperaçãoIdempotente?Por quê?
GET /beneficiarios/1 ✅ Sim Ler não altera nada. 1x ou 1000x = mesmo resultado.
PUT /beneficiarios/1 ✅ Sim Substituir com os mesmos dados 1x ou 10x = mesmo estado final.
DELETE /beneficiarios/1 ✅ Sim Apagar 1x = recurso gone. Apagar 10x = ainda gone (404).
POST /beneficiarios ❌ Não Cada chamada cria um novo registro. 3 chamadas = 3 beneficiários.

Por que Idempotência Importa?

Redes são não confiáveis. Imagine este cenário:

  1. O Front-end envia um POST /doacoes.
  2. O servidor processa e cria a doação com sucesso.
  3. A resposta se perde na rede (timeout).
  4. O Front-end, achando que falhou, reenvia o mesmo POST.
  5. Resultado: doação duplicada no banco.

Soluções para POST Idempotente

  • Validação de unicidade: Verificar se já existe um registro com os mesmos dados (ex: CPF, combinação doador+data+valor).
  • Idempotency-Key: O cliente envia um cabeçalho Idempotency-Key: uuid-123. O servidor verifica se já processou essa chave.
✅ Na SocialConnect: O POST de beneficiário já é protegido contra duplicação pela validação de CPF único (existsByCpf). Isso torna a operação "efetivamente idempotente" para o caso mais comum.

⚠️ Armadilhas Comuns

1. Retornar 200 no POST

❌ Errado: return ResponseEntity.ok(salvo);

✅ Correto: return ResponseEntity.created(location).body(salvo);

2. PUT parcial (esquecer campos)

❌ Problema: O cliente envia apenas nome no PUT. Os demais campos viram null.

✅ Solução: Use PATCH para atualizações parciais. PUT exige todos os campos.

3. Paginação sem total

❌ Errado: Retornar List<T> em vez de Page<T>.

✅ Correto: Use Page<T> para incluir totalElements e totalPages.

4. Filtros hardcoded

❌ Errado: Criar /doacoes/por-data, /doacoes/por-tipo, etc.

✅ Correto: Use query parameters opcionais: /doacoes?dataInicio=...&tipo=...

5. Ignorar idempotência no POST

❌ Problema: POST duplicado cria registros repetidos.

✅ Solução: Valide unicidade (ex: existsByCpf) e retorne 409 Conflict.

📝 Resumo da Aula

  • Semântica HTTP é o contrato invisível entre API e cliente. Use os métodos e status codes corretos.
  • DTOs separados (Request/Response) garantem segurança, clareza e desacoplamento.
  • PUT substitui tudo; PATCH atualiza parcialmente.
  • Paginação (Pageable + Page<T>) é obrigatória para listas grandes.
  • Filtros dinâmicos via query parameters opcionais tornam a API flexível.
  • Idempotência protege contra duplicações em redes instáveis.
