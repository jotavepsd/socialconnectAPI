Aula 06: Validação, Erros (RFC 7807) e Swagger

Tópicos Especiais em Sistemas para Internet III | Material Didático Completo

🏆 REGRA DE OURO DA DISCIPLINA: Toda API deve ter documentação OpenAPI/Swagger completa, navegável e com exemplos de requisições/respostas. Sem Swagger = nota reduzida na A1.

🎯 Objetivos de Aprendizagem

Ao final desta aula, você será capaz de:

  • Aplicar Bean Validation para validar dados de entrada (DTOs).
  • Implementar Problem Details (RFC 7807) para padronizar respostas de erro.
  • Configurar internacionalização (i18n) para mensagens em português.
  • Documentar APIs com SpringDoc OpenAPI usando anotações.
  • Navegar e testar endpoints no Swagger UI.
  • Customizar exemplos de requisições e respostas na documentação.

📖 Contexto da Aula

Nas aulas anteriores (03-05), construímos o CRUD de Beneficiários com semântica HTTP rigorosa. Mas e quando o cliente envia dados inválidos?

Problemas que vamos resolver:

  • ❌ Cliente envia CPF com letras → API aceita e grava lixo no banco.
  • ❌ Cliente envia nome vazio → API grava registro sem nome.
  • ❌ Ocorre um erro → API retorna {"error": "erro"} sem detalhes.
  • ❌ Cliente quer testar a API → Não sabe quais campos enviar.
  • ❌ Front-end quer integrar → Não tem documentação clara.
✅ Soluções desta aula:
  • Bean Validation: Valida dados antes de chegar ao Service.
  • Problem Details: Respostas de erro padronizadas e ricas em detalhes.
  • Swagger: Documentação viva e navegável para clientes.

📋 O que é Bean Validation?

Bean Validation (Jakarta Validation) é uma especificação Java que permite declarar regras de validação diretamente nas classes (DTOs, Entities) usando anotações.

Por que usar?

  • Declarativo: Regras ficam no código, não espalhadas em ifs.
  • Reutilizável: Mesmas anotações em qualquer DTO.
  • Integrado: Spring Boot valida automaticamente com @Valid.
  • Padronizado: Mensagens de erro consistentes.

Fluxo de Validação

Cliente envia JSON
    ↓
Controller recebe com @Valid
    ↓
Spring valida automaticamente
    ↓
Se inválido → 400 Bad Request com detalhes
Se válido → Continua para o Service

🏷️ Anotações de Validação Comuns

Anotação Uso Exemplo
@NotNull Não pode ser null @NotNull Long id
@NotBlank Não pode ser null, vazio ou espaços @NotBlank String nome
@Size Tamanho mínimo/máximo @Size(min=3, max=50) String nome
@Email Formato de email válido @Email String email
@Pattern Regex personalizada @Pattern(regexp="\\d{11}") String cpf
@Min / @Max Valor mínimo/máximo @Min(0) Integer idade
@Past / @Future Data passada/futura @Past LocalDate nascimento
💡 Dica: Todas as anotações aceitam o parâmetro message para customizar a mensagem de erro: 
@NotBlank(message = "Nome é obrigatório")
String nome;

💻 Implementação: DTO com Validação

BeneficiarioRequestDTO.java

package br.com.socialconnect.api.beneficiarios.dto;

import jakarta.validation.constraints.*;

public record BeneficiarioRequestDTO(

    @NotBlank(message = "Nome é obrigatório")
    @Size(max = 150, message = "Nome deve ter no máximo 150 caracteres")
    String nome,

    @NotBlank(message = "CPF é obrigatório")
    @Pattern(
        regexp = "\\d{11}|\\d{14}",
        message = "CPF deve ter 11 ou 14 dígitos"
    )
    String cpf,

    @Size(max = 20, message = "Telefone deve ter no máximo 20 caracteres")
    String telefone,

    @Size(max = 255, message = "Endereço deve ter no máximo 255 caracteres")
    String endereco,

    @Size(max = 500, message = "Situação deve ter no máximo 500 caracteres")
    String situacaoVulnerabilidade

) {}

Controller com @Valid

@PostMapping
public ResponseEntity<BeneficiarioResponseDTO> criar(
        @Valid @RequestBody BeneficiarioRequestDTO dto) {
    BeneficiarioResponseDTO salvo = service.criar(dto);
    URI location = URI.create("/api/v1/beneficiarios/" + salvo.idBeneficiario());
    return ResponseEntity.created(location).body(salvo);
}
💡 O que acontece:
  • O @Valid dispara a validação automática do Spring.
  • Se houver erros, o Spring lança MethodArgumentNotValidException.
  • Por padrão, retorna 400 Bad Request com lista de erros.
  • Na próxima seção, vamos customizar essa resposta com Problem Details.

🔧 Validações Customizadas

Para validações complexas (ex: validar CPF com dígito verificador), crie anotações personalizadas:

1. Criar a Anotação

package br.com.socialconnect.api.validation;

import jakarta.validation.*;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = CpfValidator.class)
@Target({ ElementType.FIELD })
@Retention(RetentionPolicy.RUNTIME)
public @interface CPF {
    String message() default "CPF inválido";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

2. Criar o Validator

package br.com.socialconnect.api.validation;

import jakarta.validation.*;

public class CpfValidator implements ConstraintValidator<CPF, String> {

    @Override
    public boolean isValid(String cpf, ConstraintValidatorContext context) {
        if (cpf == null || cpf.isBlank()) return true; // Use @NotBlank para obrigar
        
        cpf = cpf.replaceAll("\\D", ""); // Remove não-dígitos
        
        if (cpf.length() != 11) return false;
        
        // Lógica de validação do CPF (dígitos verificadores)
        // ... implementação simplificada ...
        
        return true;
    }
}

3. Usar no DTO

public record BeneficiarioRequestDTO(
    @NotBlank String nome,
    
    @CPF // ← Anotação customizada
    String cpf,
    
    String telefone
) {}
✅ Benefícios:
  • Reutilizável em qualquer DTO que tenha CPF.
  • Mensagem de erro padronizada.
  • Lógica de validação centralizada.

📄 O que é RFC 7807 (Problem Details)?

A RFC 7807 é um padrão da IETF que define um formato JSON padronizado para respostas de erro em APIs HTTP.

Por que usar?

  • Padronização: Todos os erros seguem o mesmo formato.
  • Riqueza de detalhes: Inclui tipo, título, status, detalhes e instância.
  • Machine-readable: Clientes podem processar erros automaticamente.
  • Human-readable: Desenvolvedores entendem o erro rapidamente.

Exemplo de Resposta de Erro

{
  "type": "https://socialconnect.api/errors/cpf-duplicado",
  "title": "CPF já cadastrado",
  "status": 409,
  "detail": "O CPF 12345678900 já está cadastrado no sistema.",
  "instance": "/api/v1/beneficiarios",
  "timestamp": "2026-08-29T14:30:00Z"
}

🏗️ Estrutura do Problem Details

Campo Tipo Descrição Obrigatório?
type URI Identificador do tipo de erro (documentação) Não
title String Resumo legível do erro Sim
status Integer Código HTTP do erro Sim
detail String Descrição detalhada do erro específico Não
instance URI Identificador da ocorrência do erro Não
💡 Campos adicionais: Você pode adicionar campos customizados (ex: timestamp, errors para lista de validação).

💻 Implementação no Spring Boot

1. Criar a Classe ProblemDetail

package br.com.socialconnect.api.exception;

import java.time.LocalDateTime;
import java.util.List;

public record ProblemDetail(
    String type,
    String title,
    int status,
    String detail,
    String instance,
    LocalDateTime timestamp,
    List<FieldError> errors
) {
    public record FieldError(
        String field,
        String message
    ) {}
}

2. Criar Exceções de Negócio

package br.com.socialconnect.api.exception;

public class CpfDuplicadoException extends RuntimeException {
    private final String cpf;

    public CpfDuplicadoException(String cpf) {
        super("CPF já cadastrado: " + cpf);
        this.cpf = cpf;
    }

    public String getCpf() {
        return cpf;
    }
}

public class RecursoNaoEncontradoException extends RuntimeException {
    public RecursoNaoEncontradoException(String message) {
        super(message);
    }
}

⚙️ Exception Handler Global

package br.com.socialconnect.api.exception;

import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.bind.MethodArgumentNotValidException;
import java.time.LocalDateTime;
import java.util.List;
import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalExceptionHandler {

    // ✅ Erro de validação (400)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ProblemDetail> handleValidation(
            MethodArgumentNotValidException ex, WebRequest request) {
        
        List<ProblemDetail.FieldError> errors = ex.getBindingResult()
            .getFieldErrors().stream()
            .map(e -> new ProblemDetail.FieldError(
                e.getField(), 
                e.getDefaultMessage()
            ))
            .collect(Collectors.toList());

        ProblemDetail problem = new ProblemDetail(
            "https://socialconnect.api/errors/validacao",
            "Erro de validação",
            HttpStatus.BAD_REQUEST.value(),
            "Um ou mais campos são inválidos.",
            request.getDescription(false),
            LocalDateTime.now(),
            errors
        );

        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem);
    }

    // ✅ CPF duplicado (409)
    @ExceptionHandler(CpfDuplicadoException.class)
    public ResponseEntity<ProblemDetail> handleCpfDuplicado(
            CpfDuplicadoException ex, WebRequest request) {
        
        ProblemDetail problem = new ProblemDetail(
            "https://socialconnect.api/errors/cpf-duplicado",
            "CPF já cadastrado",
            HttpStatus.CONFLICT.value(),
            ex.getMessage(),
            request.getDescription(false),
            LocalDateTime.now(),
            List.of()
        );

        return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
    }

    // ✅ Recurso não encontrado (404)
    @ExceptionHandler(RecursoNaoEncontradoException.class)
    public ResponseEntity<ProblemDetail> handleNaoEncontrado(
            RecursoNaoEncontradoException ex, WebRequest request) {
        
        ProblemDetail problem = new ProblemDetail(
            "https://socialconnect.api/errors/nao-encontrado",
            "Recurso não encontrado",
            HttpStatus.NOT_FOUND.value(),
            ex.getMessage(),
            request.getDescription(false),
            LocalDateTime.now(),
            List.of()
        );

        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }

    // ✅ Erro genérico (500)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleGenerico(
            Exception ex, WebRequest request) {
        
        ProblemDetail problem = new ProblemDetail(
            "https://socialconnect.api/errors/erro-interno",
            "Erro interno do servidor",
            HttpStatus.INTERNAL_SERVER_ERROR.value(),
            "Ocorreu um erro inesperado. Tente novamente.",
            request.getDescription(false),
            LocalDateTime.now(),
            List.of()
        );

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(problem);
    }
}
✅ Resultado: Agora todas as respostas de erro seguem o padrão RFC 7807, com detalhes ricos e consistentes.

🌍 O que é i18n (Internacionalização)?

i18n (internationalization) é o processo de adaptar a aplicação para diferentes idiomas e regiões sem alterar o código.

Por que usar?

  • Mensagens em português: Usuários brasileiros entendem melhor.
  • Facilidade de manutenção: Mensagens ficam em arquivos separados.
  • Escalabilidade: Fácil adicionar novos idiomas no futuro.

💻 Configuração de i18n

1. Criar Arquivo de Mensagens

Em src/main/resources/messages.properties:

# Mensagens de validação
NotBlank.nome=Nome é obrigatório
Size.nome=Nome deve ter no máximo {1} caracteres
NotBlank.cpf=CPF é obrigatório
Pattern.cpf=CPF deve ter 11 ou 14 dígitos

# Mensagens de negócio
cpf.duplicado=O CPF {0} já está cadastrado no sistema.
recurso.nao.encontrado=Recurso não encontrado: {0}

2. Configurar MessageSource

package br.com.socialconnect.api.config;

import org.springframework.context.*;
import org.springframework.context.annotation.*;
import org.springframework.web.servlet.LocaleResolver;
import org.springframework.web.servlet.i18n.FixedLocaleResolver;
import java.util.Locale;

@Configuration
public class I18nConfig {

    @Bean
    public MessageSource messageSource() {
        ResourceBundleMessageSource source = new ResourceBundleMessageSource();
        source.setBasename("messages");
        source.setDefaultEncoding("UTF-8");
        return source;
    }

    @Bean
    public LocaleResolver localeResolver() {
        // Força português do Brasil
        return new FixedLocaleResolver(new Locale("pt", "BR"));
    }
}

3. Usar no DTO

public record BeneficiarioRequestDTO(
    @NotBlank(message = "{NotBlank.nome}")
    String nome,
    
    @NotBlank(message = "{NotBlank.cpf}")
    String cpf
) {}
💡 Nota: As chaves {NotBlank.nome} são resolvidas automaticamente pelo Spring usando o MessageSource.

📘 O que é OpenAPI?

OpenAPI (anteriormente Swagger) é uma especificação para descrever APIs RESTful em formato YAML ou JSON. Ela define:

  • Endpoints disponíveis (paths)
  • Operações (GET, POST, PUT, DELETE)
  • Parâmetros (query, path, body)
  • Respostas (status codes, schemas)
  • Modelos de dados (schemas)

Por que usar?

  • Documentação viva: Atualiza automaticamente com o código.
  • Geração de clientes: Front-end pode gerar código automaticamente.
  • Testes: Swagger UI permite testar endpoints diretamente.
  • Contrato claro: Define o acordo entre back-end e front-end.

🖥️ O que é Swagger UI?

Swagger UI é uma interface web gerada automaticamente a partir da especificação OpenAPI. Ela permite:

  • Visualizar todos os endpoints da API
  • Ver detalhes de cada operação (parâmetros, respostas)
  • Testar endpoints diretamente no navegador
  • Ver exemplos de requisições e respostas

Acesso

GET http://localhost:8080/swagger-ui.html

🧭 Navegando no Swagger UI

Estrutura da Interface

  1. Tags: Endpoints agrupados por recurso (Beneficiários, Doadores, Doações)
  2. Operações: Cada endpoint com método HTTP (GET, POST, etc.)
  3. Try it out: Botão para testar o endpoint
  4. Execute: Executa a requisição e mostra a resposta

Passo a Passo para Testar

  1. Clique em uma tag (ex: "Beneficiários")
  2. Clique em um endpoint (ex: POST /api/v1/beneficiarios)
  3. Clique em "Try it out"
  4. Preencha os parâmetros (ou use o exemplo)
  5. Clique em "Execute"
  6. Veja a resposta (status, body, headers)
✅ Dica: O Swagger UI é a melhor forma de explorar a API antes de integrar com o Front-end.

⚠️ Armadilhas Comuns

1. Esquecer @Valid no Controller

❌ Errado: @RequestBody BeneficiarioRequestDTO dto

✅ Correto: @Valid @RequestBody BeneficiarioRequestDTO dto

Sintoma: Validação não é executada, dados inválidos chegam ao Service.

2. Mensagens de erro em inglês

❌ Errado: "must not be blank"

✅ Correto: Configurar i18n com messages.properties

3. Retornar stack trace no erro

❌ Errado: Expor detalhes internos do servidor (security risk)

✅ Correto: Usar Problem Details com mensagem genérica para 500

4. Swagger sem exemplos

❌ Errado: Campos vazios no Swagger UI

✅ Correto: Usar @Schema(example = "...") nos DTOs

5. Não documentar todos os status codes

❌ Errado: Apenas @ApiResponse(responseCode = "200")

✅ Correto: Documentar 200, 201, 400, 404, 409, 500

📝 Resumo da Aula

  • SpringDoc OpenAPI: Documente endpoints com anotações (@Tag, @Operation, @ApiResponse).
  • Swagger UI: Interface web para navegar e testar a API.
  • Exemplos: Use @Schema(example = "...") para facilitar testes.
