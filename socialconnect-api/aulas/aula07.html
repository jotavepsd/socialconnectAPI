🎯 Objetivos de Aprendizagem

  • Compreender a diferença entre testes unitários (rápidos, mockados) e de integração (lentos, banco real).
  • Aplicar o padrão AAA (Arrange-Act-Assert) com comentários explícitos, conforme o padrão do repositório.
  • Usar @ExtendWith(MockitoExtension.class) para testes unitários puros, sem a sobrecarga do @SpringBootTest.
  • Configurar e utilizar o Testcontainers para subir um PostgreSQL 17 efêmero durante os testes de integração.

🧪 O Padrão de Testes Unitários do Nosso Repo

Observe que nos arquivos de teste do repositório (BeneficiarioServiceTest e DoacaoServiceTest), não usamos @SpringBootTest. Em vez disso, usamos:

@ExtendWith(MockitoExtension.class)
class DoacaoServiceTest {
    @Mock
    private DoacaoRepository doacaoRepository;

    @InjectMocks
    private DoacaoService doacaoService;
    // ...
}
💡 Por que isso é melhor?
O @SpringBootTest sobe todo o contexto da aplicação (banco, segurança, beans), o que pode levar segundos. O @ExtendWith(MockitoExtension.class) é instantâneo e isola perfeitamente a lógica de negócio, que é o objetivo de um teste unitário.

💻 Exemplo Real do Repositório: DoacaoServiceTest

Este é o código exato que já está no seu repositório. Note a clareza dos comentários ARRANGE, ACT, ASSERT:

@Test
@DisplayName("Deve criar doação quando dados válidos")
void deveCriarDoacaoQuandoDadosValidos() {
    // ==========================================
    // ARRANGE: Preparar o cenário
    // ==========================================
    DoacaoRequestDTO dto = new DoacaoRequestDTO(
        1L, LocalDate.of(2026, 9, 11), new BigDecimal("100.00"), 
        TipoDoacao.ALIMENTO, "Doação de teste"
    );
    
    Doacao doacaoSalva = Doacao.builder().idDoacao(1L).build();
    Mockito.when(doacaoRepository.save(Mockito.any())).thenReturn(doacaoSalva);

    // ==========================================
    // ACT: Executar a ação
    // ==========================================
    DoacaoResponseDTO resultado = doacaoService.criar(dto);

    // ==========================================
    // ASSERT: Verificar o resultado
    // ==========================================
    Assertions.assertNotNull(resultado.idDoacao(), "ID da doação não deve ser nulo");
    Assertions.assertEquals(new BigDecimal("100.00"), resultado.valor());
    Mockito.verify(doacaoRepository, Mockito.times(1)).save(Mockito.any());
}

⚙️ Configuração de Teste (Já presente no repo)

O repositório já possui o arquivo application-test.properties configurado para usar o Testcontainers:

# Usar Testcontainers para subir um PostgreSQL real
spring.datasource.url=jdbc:tc:postgresql:17:///testdb
spring.datasource.driver-class-name=org.testcontainers.jdbc.ContainerDatabaseDriver
spring.datasource.username=test
spring.datasource.password=test

# JPA/Hibernate
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
spring.jpa.hibernate.ddl-auto=validate

# Flyway (executa as migrations no banco do Testcontainers)
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
✅ Vantagem: Ao rodar testes de integração, o Spring detectará este perfil e usará o PostgreSQL real, garantindo que as migrations do Flyway e as constraints do JPA funcionam exatamente como em produção.

🔄 TDD: Test-Driven Development

O ciclo que praticaremos no Dojo:

  1. RED: Escrever um teste que falha (ex: tentar salvar doação com data futura).
  2. GREEN: Implementar a validação @DataNaoFutura no DTO para o teste passar.
  3. REFACTOR: Melhorar a mensagem de erro no messages.properties sem quebrar o teste.

🎯 Desafio para as Duplas:
  1. Complementar o DoacaoServiceTest.java: Adicionar o teste deveLancarExcecaoQuandoDoadorNaoExistir (mockar o DoadorRepository para retornar Optional.empty()).
  2. Criar o DoacaoControllerIntegrationTest.java:
    • Usar @SpringBootTest(webEnvironment = RANDOM_PORT) e @Testcontainers.
    • Testar POST /api/v1/doacoes com dados válidos (esperar 201 Created).
    • Testar POST /api/v1/doacoes com dataDoacao no futuro (esperar 400 Bad Request com Problem Details).

Regras: Use o padrão AAA com comentários. Execute mvn test antes de finalizar. Duas duplas serão sorteadas para apresentar a solução.

⚠️ Armadilhas Comuns

  • Esquecer o Mockito.when: O mock retorna null por padrão, causando NullPointerException no passo ACT.
  • Usar @SpringBootTest em testes unitários: Deixa a suíte de testes lenta desnecessariamente. Reserve-o para integração.
  • Não limpar o banco entre testes de integração: Use @DirtiesContext ou scripts de limpeza se os testes começarem a interferir uns nos outros.
  • Testar detalhes de implementação: Foque no comportamento (entrada → saída), não em quantas vezes um método privado foi chamado.
