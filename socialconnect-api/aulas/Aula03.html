Aula 03: Spring Boot e Arquitetura em Camadas

Tópicos Especiais em Sistemas para Internet III | Material Didático Completo

🏆 REGRA DE OURO DA DISCIPLINA: Chaves primárias no banco de dados DEVEM usar o prefixo id_ (ex: id_beneficiario, id_doacao).

🎯 Objetivos de Aprendizagem

Ao final desta aula, você será capaz de:

  • Compreender a importância da separação de responsabilidades em uma aplicação web moderna.
  • Implementar uma arquitetura em camadas (Controller, Service, Repository) seguindo os princípios SOLID.
  • Aplicar injeção de dependência via construtor, evitando o uso de @Autowired em campos.
  • Utilizar record do Java 21 para criar DTOs imutáveis e concisos.
  • Garantir semântica HTTP correta com ResponseEntity (200 OK, 201 Created, 204 No Content, etc.).
  • Aplicar o padrão id_ para chaves primárias, tanto no mapeamento JPA quanto na documentação OpenAPI.

📖 Contexto da Aula

Na Aula 02, você criou o contrato OpenAPI da API SocialConnect, definindo os recursos (/beneficiarios, /doadores, /doacoes) e seus endpoints. Esse contrato é o "contrato" entre o back-end e o front-end (ou qualquer consumidor da API).

Agora, na Aula 03, vamos transformar esse contrato em código funcional. Mas não vamos apenas "jogar código" em um único arquivo. Vamos estruturar a aplicação em camadas bem definidas, seguindo as melhores práticas da indústria.

💡 Por que separar em camadas?
Imagine que você precisa mudar o banco de dados de H2 para PostgreSQL. Se toda a lógica de negócio estiver misturada com o código HTTP, você terá que refatorar tudo. Com camadas bem definidas, você muda apenas a camada de Repository, e o resto do sistema continua funcionando.

🏗️ Arquitetura em Camadas

A arquitetura em camadas (também chamada de arquitetura multicamadas ou layered architecture) é um padrão de design que organiza o código em grupos de responsabilidade bem definidos. Cada camada tem um papel específico e se comunica apenas com as camadas adjacentes.

As 4 Camadas Principais

Controller
(HTTP)

Camada Responsabilidade Anotação Spring Exemplo

Service Conter a regra de negócio, orquestrar operações, validar regras complexas @Service BeneficiarioService
Repository Interagir com o banco de dados (CRUD, queries personalizadas) @Repository BeneficiarioRepository
Model/Entity Representar a estrutura de dados e o mapeamento ORM @Entity Beneficiario

Fluxo de uma Requisição Típica

  1. Cliente envia uma requisição HTTP (ex: POST /api/v1/beneficiarios).
  2. Controller recebe a requisição, extrai os dados do corpo (JSON) e chama o Service.
  3. Service aplica a regra de negócio (ex: verificar se o CPF já existe) e chama o Repository.
  4. Repository persiste os dados no banco de dados e retorna a entidade salva.
  5. Service converte a entidade em DTO (para não expor a estrutura interna) e retorna ao Controller.
  6. Controller devolve a resposta HTTP com o status correto (ex: 201 Created).
✅ Benefícios dessa abordagem:
  • Testabilidade: Cada camada pode ser testada isoladamente (testes unitários).
  • Manutenibilidade: Mudanças em uma camada não afetam as outras.
  • Reutilização: O Service pode ser usado por múltiplos Controllers (ex: API REST e GraphQL).
  • Segurança: A camada de Service pode aplicar validações de segurança antes de acessar o banco.

⚡ Princípios SOLID Aplicados

Os princípios SOLID são cinco diretrizes de design que ajudam a criar software mais flexível, manutenível e escalável. Nesta aula, vamos focar em dois deles:

1. Single Responsibility Principle (SRP) - Princípio da Responsabilidade Única

Definição: Uma classe deve ter apenas um motivo para mudar.

Exemplo prático:
O BeneficiarioController deve apenas lidar com HTTP (receber requisições, devolver respostas). Ele NÃO deve conter lógica de negócio (ex: verificar se o CPF é válido). Essa lógica vai para o BeneficiarioService.

2. Dependency Inversion Principle (DIP) - Princípio da Inversão de Dependência

Definição: Módulos de alto nível não devem depender de módulos de baixo nível. Ambos devem depender de abstrações.

Exemplo prático:
O BeneficiarioService não deve criar diretamente uma instância de BeneficiarioRepository. Em vez disso, ele recebe o Repository por injeção de dependência. Isso permite, por exemplo, trocar o Repository por um mock durante os testes.

💉 Injeção de Dependência (DI)

A Injeção de Dependência é um padrão de design onde um objeto recebe suas dependências (outros objetos que ele precisa para funcionar) de fontes externas, em vez de criá-las internamente.

Por que usar Injeção de Dependência?

  • Desacoplamento: As classes não ficam "presas" a implementações específicas.
  • Testabilidade: Facilita a criação de testes unitários com mocks.
  • Flexibilidade: Permite trocar implementações sem alterar o código (ex: trocar H2 por PostgreSQL).

Formas de Injeção de Dependência no Spring

❌ Forma NÃO Recomendada: Injeção por Campo

@Service
public class BeneficiarioService {

    @Autowired // ⚠️ Evite essa abordagem
    private BeneficiarioRepository repository;
}

Problemas:

  • Dificulta testes unitários (você precisa do contexto do Spring para injetar a dependência).
  • Permite que o campo seja alterado após a construção do objeto (violando imutabilidade).
  • Esconde as dependências da classe (quem lê o código não sabe quais dependências são necessárias).

✅ Forma Recomendada: Injeção por Construtor

@Service
public class BeneficiarioService {

    private final BeneficiarioRepository repository;

    // ✅ Injeção via construtor (padrão da disciplina)
    public BeneficiarioService(BeneficiarioRepository repository) {
        this.repository = repository;
    }
}

Vantagens:

  • Imutabilidade: O campo é final, garantindo que não será alterado.
  • Testabilidade: Você pode criar o Service manualmente em testes, passando um mock do Repository.
  • Transparência: As dependências ficam explícitas no construtor.
  • Falha rápida: Se uma dependência não estiver disponível, o erro ocorre na inicialização, não em tempo de execução.
✅ Regra da Disciplina: Sempre use injeção de dependência via construtor com campos final. Não use @Autowired em campos.

📦 DTOs e Records do Java 21

O que é um DTO?

DTO (Data Transfer Object) é um objeto simples que carrega dados entre processos. Ele é usado para transferir dados entre camadas (ex: entre o Controller e o Service) ou entre sistemas (ex: entre o back-end e o front-end).

Por que usar DTOs em vez de Entities?

  • Segurança: Você controla quais dados são expostos. A Entity pode ter campos sensíveis (ex: senha) que não devem ir para o cliente.
  • Flexibilidade: O DTO pode ter uma estrutura diferente da Entity (ex: combinar dados de múltiplas tabelas).
  • Desacoplamento: Mudanças na Entity não afetam diretamente o contrato da API.
  • Performance: Você pode carregar apenas os dados necessários, evitando o problema de "N+1 queries".

Records do Java 21

Um record é um tipo especial de classe introduzido no Java 14 (e consolidado no Java 16+) que é imutável por padrão. Ele gera automaticamente:

  • Construtor com todos os campos.
  • Getters (sem o prefixo "get", apenas o nome do campo).
  • Métodos equals(), hashCode() e toString().

Exemplo: DTO com Record

public record BeneficiarioDTO(
    Long idBeneficiario,
    String nome,
    String cpf,
    String telefone,
    String endereco,
    String situacaoVulnerabilidade,
    LocalDate dataCadastro
) {}

Como usar o Record:

// Criação
BeneficiarioDTO dto = new BeneficiarioDTO(
    1L, "Maria da Silva", "12345678900", 
    "11999999999", "Rua das Flores", 
    "Renda familiar baixa", LocalDate.now()
);

// Acesso aos campos (sem "get")
System.out.println(dto.nome()); // "Maria da Silva"
System.out.println(dto.cpf()); // "12345678900"
💡 Dica: Records são ideais para DTOs porque são imutáveis (você não pode alterar os dados após a criação) e concisos (menos código boilerplate).

🌐 Semântica HTTP e ResponseEntity

A semântica HTTP refere-se ao uso correto dos códigos de status, métodos HTTP e cabeçalhos para comunicar o resultado de uma operação. Usar a semântica correta é essencial para uma API RESTful robusta.

Códigos de Status HTTP Mais Comuns

Código Significado Quando Usar
200 OK Requisição bem-sucedida GET, PUT (com corpo de resposta)
201 Created Recurso criado com sucesso POST (com cabeçalho Location)
204 No Content Requisição bem-sucedida, sem corpo de resposta DELETE, PUT (sem corpo)
400 Bad Request Requisição inválida (erro do cliente) Validação de dados falhou
404 Not Found Recurso não encontrado ID inexistente
500 Internal Server Error Erro interno do servidor Exceção não tratada

ResponseEntity no Spring

O ResponseEntity é uma classe do Spring que permite construir respostas HTTP completas, incluindo status, cabeçalhos e corpo.

Exemplos de Uso:

// 200 OK com corpo
return ResponseEntity.ok(dto);

// 201 Created com cabeçalho Location
URI location = URI.create("/api/v1/beneficiarios/" + dto.idBeneficiario());
return ResponseEntity.created(location).body(dto);

// 204 No Content (sem corpo)
return ResponseEntity.noContent().build();

// 404 Not Found
return ResponseEntity.notFound().build();
✅ Regra da Disciplina: Sempre use ResponseEntity para devolver respostas HTTP. Nunca retorne diretamente a entidade ou DTO (ex: return dto;), pois isso não permite controlar o status HTTP.

1️⃣ Implementação: Entidade JPA

A entidade JPA representa a estrutura de dados no banco de dados. Ela é mapeada para uma tabela usando anotações do JPA.

Beneficiario.java

package br.com.socialconnect.api.beneficiarios.model;

import jakarta.persistence.*;
import lombok.*;
import java.time.LocalDate;

@Entity // Marca como entidade JPA
@Table(name = "beneficiarios") // Nome da tabela no banco
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder // Lombok gera construtores e builders
public class Beneficiario {

    @Id // Chave primária
    @GeneratedValue(strategy = GenerationType.IDENTITY) // Auto-incremento
    @Column(name = "id_beneficiario") // ⚠️ Padrão id_ no banco
    private Long idBeneficiario; // CamelCase no Java

    @Column(nullable = false, length = 150)
    private String nome;

    @Column(nullable = false, unique = true, length = 14)
    private String cpf;

    @Column(length = 20)
    private String telefone;

    @Column(length = 255)
    private String endereco;

    @Column(name = "situacao_vulnerabilidade", length = 500)
    private String situacaoVulnerabilidade;

    @Column(name = "data_cadastro", nullable = false)
    private LocalDate dataCadastro;
}
💡 Observação importante:
O atributo na classe Java é idBeneficiario (camelCase), mas a coluna no banco é id_beneficiario (snake_case com prefixo id_). O mapeamento é feito pela anotação @Column(name = "id_beneficiario").

2️⃣ Implementação: DTO com Record

O DTO é usado para transferir dados entre as camadas e para expor os dados na API. Ele não deve expor a entidade JPA diretamente.

BeneficiarioDTO.java

package br.com.socialconnect.api.beneficiarios.dto;

import java.time.LocalDate;

// Record é imutável, conciso e ideal para DTOs no Java 21+
public record BeneficiarioDTO(
    Long idBeneficiario,
    String nome,
    String cpf,
    String telefone,
    String endereco,
    String situacaoVulnerabilidade,
    LocalDate dataCadastro
) {}
✅ Vantagens do Record:
  • Imutabilidade garantida (os dados não podem ser alterados após a criação).
  • Código conciso (sem getters, setters, construtores boilerplate).
  • Métodos equals(), hashCode() e toString() gerados automaticamente.
  • Ideal para DTOs porque são simples containers de dados.

3️⃣ Implementação: Camada de Serviço

O Service contém a lógica de negócio da aplicação. Ele orquestra as operações, aplica validações e chama o Repository para persistir os dados.

BeneficiarioService.java

package br.com.socialconnect.api.beneficiarios.service;

import br.com.socialconnect.api.beneficiarios.dto.BeneficiarioDTO;
import br.com.socialconnect.api.beneficiarios.model.Beneficiario;
import br.com.socialconnect.api.beneficiarios.repository.BeneficiarioRepository;
import org.springframework.stereotype.Service;
import java.util.List;

@Service // Marca como um bean gerenciado pelo Spring
public class BeneficiarioService {

    private final BeneficiarioRepository repository;

    // ✅ Injeção de dependência via construtor (padrão da disciplina)
    public BeneficiarioService(BeneficiarioRepository repository) {
        this.repository = repository;
    }

    // Lista todos os beneficiários
    public List<BeneficiarioDTO> listarTodos() {
        return repository.findAll().stream()
                .map(this::toDTO) // Converte Entity para DTO
                .toList();
    }

    // Busca um beneficiário por ID
    public BeneficiarioDTO buscarPorId(Long idBeneficiario) {
        Beneficiario beneficiario = repository.findById(idBeneficiario)
                .orElseThrow(() -> new RuntimeException(
                    "Beneficiário não encontrado com o ID: " + idBeneficiario
                ));
        return toDTO(beneficiario);
    }

    // Salva um novo beneficiário
    public BeneficiarioDTO salvar(BeneficiarioDTO dto) {
        Beneficiario beneficiario = toEntity(dto); // Converte DTO para Entity
        beneficiario = repository.save(beneficiario); // Persiste no banco
        return toDTO(beneficiario); // Retorna o DTO com o ID gerado
    }

    // Deleta um beneficiário por ID
    public void deletar(Long idBeneficiario) {
        repository.deleteById(idBeneficiario);
    }

    // Métodos auxiliares para conversão entre Entity e DTO
    
    private BeneficiarioDTO toDTO(Beneficiario entity) {
        return new BeneficiarioDTO(
                entity.getIdBeneficiario(), 
                entity.getNome(), 
                entity.getCpf(),
                entity.getTelefone(), 
                entity.getEndereco(), 
                entity.getSituacaoVulnerabilidade(),
                entity.getDataCadastro()
        );
    }

    private Beneficiario toEntity(BeneficiarioDTO dto) {
        return Beneficiario.builder()
                .idBeneficiario(dto.idBeneficiario())
                .nome(dto.nome())
                .cpf(dto.cpf())
                .telefone(dto.telefone())
                .endereco(dto.endereco())
                .situacaoVulnerabilidade(dto.situacaoVulnerabilidade())
                .dataCadastro(dto.dataCadastro())
                .build();
    }
}
💡 Pontos importantes:
  • Injeção via construtor: O Repository é recebido no construtor e armazenado em um campo final.
  • Conversão Entity ↔ DTO: Os métodos toDTO() e toEntity() fazem a conversão entre as camadas.
  • Tratamento de erros: O método buscarPorId() lança uma exceção se o beneficiário não for encontrado (na Aula 06, vamos tratar isso com Problem Details).
  • Builder pattern: O Lombok gera o método builder() para criar objetos de forma fluente.

4️⃣ Implementação: Controller REST

O Controller é a porta de entrada da API. Ele recebe as requisições HTTP, chama o Service apropriado e devolve a resposta HTTP com o status correto.

BeneficiarioController.java

package br.com.socialconnect.api.beneficiarios.controller;

import br.com.socialconnect.api.beneficiarios.dto.BeneficiarioDTO;
import br.com.socialconnect.api.beneficiarios.service.BeneficiarioService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.util.List;

@RestController // Marca como um controller REST
@RequestMapping("/api/v1/beneficiarios") // URL base para todos os endpoints
public class BeneficiarioController {

    private final BeneficiarioService service;

    // ✅ Injeção de dependência via construtor
    public BeneficiarioController(BeneficiarioService service) {
        this.service = service;
    }

    // GET /api/v1/beneficiarios - Lista todos os beneficiários
    @GetMapping
    public ResponseEntity<List<BeneficiarioDTO>> listarTodos() {
        return ResponseEntity.ok(service.listarTodos()); // 200 OK
    }

    // GET /api/v1/beneficiarios/{idBeneficiario} - Busca por ID
    @GetMapping("/{idBeneficiario}")
    public ResponseEntity<BeneficiarioDTO> buscarPorId(
            @PathVariable Long idBeneficiario) {
        return ResponseEntity.ok(service.buscarPorId(idBeneficiario)); // 200 OK
    }

    // POST /api/v1/beneficiarios - Cria um novo beneficiário
    @PostMapping
    public ResponseEntity<BeneficiarioDTO> salvar(
            @RequestBody BeneficiarioDTO dto) {
        BeneficiarioDTO salvo = service.salvar(dto);
        
        // ✅ Retorna 201 Created com o cabeçalho Location
        URI location = URI.create("/api/v1/beneficiarios/" + salvo.idBeneficiario());
        return ResponseEntity.created(location).body(salvo);
    }

    // DELETE /api/v1/beneficiarios/{idBeneficiario} - Deleta um beneficiário
    @DeleteMapping("/{idBeneficiario}")
    public ResponseEntity<Void> deletar(
            @PathVariable Long idBeneficiario) {
        service.deletar(idBeneficiario);
        return ResponseEntity.noContent().build(); // 204 No Content
    }
}
💡 Anotações importantes:
  • @RestController: Combina @Controller e @ResponseBody. Indica que os métodos retornam dados (JSON) em vez de views.
  • @RequestMapping: Define a URL base para todos os endpoints do controller.
  • @GetMapping, @PostMapping, @DeleteMapping: Mapeiam métodos HTTP específicos.
  • @PathVariable: Extrai valores da URL (ex: /beneficiarios/123 → idBeneficiario = 123).
  • @RequestBody: Extrai o corpo da requisição (JSON) e converte para o objeto Java.
✅ Semântica HTTP correta:
  • GET → 200 OK com corpo de resposta.
  • POST → 201 Created com cabeçalho Location apontando para o novo recurso.
  • DELETE → 204 No Content (sem corpo de resposta).

🔄 Fluxo Completo de uma Requisição

Vamos acompanhar o fluxo de uma requisição POST /api/v1/beneficiarios desde o cliente até o banco de dados e de volta.

Passo a Passo:

  1. Cliente envia a requisição: 
    POST /api/v1/beneficiarios
Content-Type: application/json

{
  "nome": "Maria da Silva",
  "cpf": "12345678900",
  "telefone": "11999999999",
  "endereco": "Rua das Flores, 123",
  "situacaoVulnerabilidade": "Renda familiar baixa",
  "dataCadastro": "2026-08-29"
}
  2. Controller recebe a requisição:
    • O Spring converte o JSON em um objeto BeneficiarioDTO (usando @RequestBody).
    • O método salvar() é chamado.
  3. Service aplica a regra de negócio:
    • Converte o DTO em Entity (toEntity()).
    • (Futuramente) Valida se o CPF já existe.
    • Chama o Repository para persistir.
  4. Repository persiste no banco:
    • O Spring Data JPA gera o SQL: INSERT INTO beneficiarios (nome, cpf, ...) VALUES (...).
    • O banco gera o id_beneficiario automaticamente.
    • Retorna a Entity salva (com o ID gerado).
  5. Service converte de volta para DTO:
    • Chama toDTO() para não expor a Entity.
    • Retorna o DTO para o Controller.
  6. Controller devolve a resposta: 
    HTTP/1.1 201 Created
Location: /api/v1/beneficiarios/1
Content-Type: application/json

{
  "idBeneficiario": 1,
  "nome": "Maria da Silva",
  "cpf": "12345678900",
  "telefone": "11999999999",
  "endereco": "Rua das Flores, 123",
  "situacaoVulnerabilidade": "Renda familiar baixa",
  "dataCadastro": "2026-08-29"
}

⚠️ Armadilhas Comuns

Durante o desenvolvimento, é comum cometer alguns erros. Aqui estão os mais frequentes e como evitá-los:

1. Esquecer as anotações @Service ou @RestController

Sintoma: Erro NoSuchBeanDefinitionException ao iniciar a aplicação.

Causa: O Spring não consegue encontrar o bean para injetar.

Solução: Adicione a anotação correta na classe.

2. Usar @Autowired em campos

Sintoma: Código funciona, mas dificulta testes e viola boas práticas.

Solução: Use injeção via construtor com campos final.

3. Underscore no nome do atributo Java

Sintoma: Erro de compilação ou convenção Java violada.

Causa: Tentar nomear o atributo como id_beneficiario (com underscore) na classe Java.

Solução: Use camelCase no Java (idBeneficiario) e mapeie para snake_case no banco com @Column(name = "id_beneficiario").

4. Esquecer o @RequestBody no POST

Sintoma: O DTO chega com todos os campos nulos.

Causa: Sem @RequestBody, o Spring tenta ligar o JSON aos parâmetros da URL.

Solução: Adicione @RequestBody no parâmetro do método.

5. Retornar diretamente a Entity no Controller

Sintoma: A API exp
